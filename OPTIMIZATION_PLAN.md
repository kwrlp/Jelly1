# План оптимизации «Музыкального хранилища» (только анализ — ничего из этого ещё не внедрено)

Сервер: 4 ГБ RAM, 2 ядра Intel, SSD 50 ГБ. Анализ основан на чтении кода v0.11; серверный конфиг (как запущены uvicorn и фронтенд, есть ли nginx) мне недоступен — см. «Шаг 0».

## Шаг 0. Сначала измерить и проверить, как запущено (30 минут, самый дешёвый выигрыш)
1. **Фронтенд должен отдаваться сборкой** (`npm run build` → статика через nginx/Caddy), а не `npm run dev`. Dev-сервер Vite отдаёт сотни неупакованных модулей и держит HMR-сокет — на 2 ядрах это заметно медленнее.
2. **Бэкенд — без `--reload`** (`uvicorn app.main:app --workers 2`, не больше числа ядер). `--reload` следит за файлами и нужен только для разработки.
3. Открыть DevTools → Network/Performance на телефоне и на ПК: понять, тормозит **сервер** (долгие ответы API, TTFB) или **браузер** (кадры, долгая отрисовка). По коду вероятны оба случая, см. ниже.
4. Включить логирование времени запросов (middleware) и `sqlalchemy` echo на один день — найти 5 самых медленных эндпоинтов и число SQL-запросов на запрос.

## A. Браузер: тяжёлая графика (вероятная причина «тормозит» именно на телефоне)
| Проблема | Где | Решение |
|---|---|---|

| 4 больших пятна с `filter: blur(80px)` + `mix-blend-mode: screen`, **анимация через `margin`** (`@keyframes drift`) — каждый кадр пересчёт раскладки | `.blob` | Анимировать только `transform`, или сделать фон статичным (один `radial-gradient`); на `prefers-reduced-motion`/слабых устройствах отключать |
| Полноэкранный SVG-шум `feTurbulence` с `mix-blend-mode: overlay`, `position: fixed` | `.bg-noise` | Заменить предрисованным PNG 160×160 или убрать |

## B. Сервер: узкие места в коде
1. **SQLite в режиме по умолчанию.** Нет WAL: любая запись блокирует чтение. Записей много: `log_event` делает `commit` на каждое посещение, прослушивание, логин, сообщение.
   → `PRAGMA journal_mode=WAL; synchronous=NORMAL; busy_timeout=5000; cache_size=-65536; temp_store=MEMORY; mmap_size=268435456` в `_sqlite_pragma`. Это единственное изменение, которое обычно даёт самый заметный эффект для SQLite под нагрузкой.
2. **Раздача аудио дорогая.** `get_file` на **каждый Range-запрос** (перемотка, докачка) делает проверку доступа: `track_accessible` → до 40 постов → для каждого `can_view_post` (3–4 запроса) и т. д. Это десятки SQL-запросов на каждые 64 КБ-запрос плеера, а стримит всё Python-генератор в потоке из пула (40 потоков).
   → один раз проверить доступ и отдать файл через **nginx `X-Accel-Redirect`** (internal location) — Python занят миллисекунды, nginx отдаёт файл с `sendfile`. Альтернатива без nginx: кэшировать результат проверки `(user_id, track_id)` на 60 с в памяти процесса.
3. **N+1 запросов.** `post_out` (автор, картинки, треки — по 3 запроса на пост), `p_out` (элементы, владелец, роль, число участников на каждый плейлист; `/playlists` грузит **все треки** каждого плейлиста), `chat_out` (последнее сообщение, непрочитанные, собеседник — на каждый чат).
   → `selectinload`/`joinedload`, один запрос на список с `GROUP BY` (как уже сделано в `with_meta` для реакций). В списках плейлистов отдавать только счётчики, треки — на странице плейлиста.
4. **Лента:** `post_out` строится для всех (до 300) постов, и только потом берётся срез `[offset:offset+20]`.
   → отобрать id и применить `offset/limit` **до** сборки; использовать keyset-пагинацию (`id < last_id`).
5. **Рекомендации (`similar_users`)** при каждом открытии ленты, «Друзей» и ответе `/recommendations/users` проходят по **всем публичным пользователям** и для каждого делают запрос (`taste_of`). Лента вызывает это дважды за загрузку страницы. Сложность O(пользователи) запросов.
   → считать раз в N минут фоновой задачей и хранить результат в таблице `user_similarity(user_id, other_id, score)`; либо кэш на 10 минут на пользователя.
6. **Поиск** (`/search`, `/tracks?q=`, админский список) выгружает 300–600 строк и фильтрует в Python (`like` с `casefold`, из-за кириллицы).
   → FTS5-таблица с токенайзером `unicode61` (регистронезависим для кириллицы) или колонки `*_norm` с нижним регистром и индексом.
7. **`/users/me` опрашивается каждые 30 с каждым клиентом** и делает ~8 `COUNT`-запросов (в т.ч. join по сообщениям).
   → хранить счётчики (непрочитанные) в самих таблицах/кэше, отдавать одним лёгким запросом; для персонала — отдельно.
8. **Недостающие индексы:** `messages(chat_id, id)` и `(chat_id, sender_id, read_at)`; `notifications(user_id, read_at)`; `tracks(owner_id, removed_at)`; `events(kind, created_at)` (статистика админки); `playlist_items(playlist_id, position)`; `posts(author_id, removed_at, id)`.
9. **`async def` + синхронная БД/диск.** `upload_track`, `upload_avatar`, `create_post`, `playlist_cover` — `async def`, но внутри синхронные запросы SQLAlchemy и запись файла: пока идёт загрузка, **цикл событий блокируется** для всех. Особенно важно после увеличения лимитов (файлы до 2 ГБ).
   → сделать обычными `def` (FastAPI выполнит в пуле потоков) или оборачивать блокирующие куски в `run_in_threadpool`. Также Starlette сначала пишет multipart во временный файл, потом мы копируем в `uploads/` — загрузка записывается на диск дважды.
10. **bcrypt** (логин/регистрация) занимает ядро ~200–300 мс; при всплеске входов 2 ядра заняты. Приемлемо, но не ставить `rounds` выше 12 и учесть при выборе числа воркеров.

## C. Сеть и обновление данных
- Опрос: чат — каждые 5 с (200 сообщений + пометка прочитанным!), список чатов — 15 с, `/users/me` — 30 с. Для 50 одновременных пользователей это ≈ 15–20 запросов/с «вхолостую».
  → увеличить интервалы и **останавливать при скрытой вкладке** (`document.visibilityState`); запрашивать только новое (`?after_id=`); позже — SSE/WebSocket для сообщений (один лёгкий поток на клиента).
- Включить сжатие (gzip/brotli) в nginx для JS/CSS/JSON; `Cache-Control: immutable` для хэшированных файлов Vite.

## D. Инфраструктура под 4 ГБ / 2 ядра
- **nginx (или Caddy) перед uvicorn:** статика фронтенда, сжатие, кэш-заголовки, `X-Accel-Redirect` для аудио, `client_max_body_size 2100m` и **`proxy_request_buffering off`** для загрузок (иначе nginx сначала складывает до 2 ГБ во временный файл).
- **Процессы:** `uvicorn --workers 2` (≈150–250 МБ на воркер). SQLite с WAL нормально работает с двумя процессами. Больше воркеров смысла нет — упрёмся в 2 ядра.
- **Кэш:** Redis не нужен. Хватит `cachetools.TTLCache` в процессе (30–120 с): настройки платформы (`get_setting` читает БД на каждый запрос), `blocked_ids`/`friend_ids`, результат проверки доступа к треку. При двух воркерах кэши раздельные — для таких TTL это допустимо.
- **Очередь задач:** Celery/Redis на 4 ГБ — избыточно. Достаточно маленькой очереди в процессе (один фоновый поток/`asyncio.Queue`) или `huey` на SQLite для: пакетной записи событий статистики (`Event`) раз в несколько секунд вместо `commit` на каждый запрос, генерации миниатюр, пересчёта рекомендаций, очистки (удаление файлов, старых событий и уведомлений).
- **Диск и квоты:** 50 ГБ при квоте 7 ГБ на пользователя — это всего ~7 «полных» пользователей. Нужны: мониторинг свободного места, отказ в загрузке при `free < 3 ГБ`, периодическая очистка сирот (файлы без записи в БД), политика для неактивных. `Track.size_bytes` — `Integer` (в SQLite это 64 бита; при переезде на PostgreSQL заменить на `BigInteger`).
- **Резервные копии:** БД — `sqlite3 .backup` по расписанию (не копировать «живой» файл при WAL).
- **Если пользователей станет много:** PostgreSQL (на 4 ГБ — `shared_buffers` ≈ 1 ГБ) вместо SQLite; но сначала пункты выше — для десятков пользователей SQLite+WAL достаточно.
